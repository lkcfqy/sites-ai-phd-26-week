# AI Systems 离线 CPU 实践包

目标：从看懂一个程序，走到能提交“可复现、有正确性对照、承认局限”的性能实验。不是跑完八条命令就精通；每课都要先预测、再运行、再解释，并完成修改任务。

## 0. 第一次运行：不需要 GPU、不需要账号密钥

1. 将 `lab_pack.py` 与本指南下载到自己新建的 `mlsys-labs` 文件夹。用文本编辑器打开脚本，确认它只导入 Python 标准库。脚本不联网、不安装依赖、不访问 GPU，只在你指定的新文件中写 JSON。
2. 打开终端，执行 `python3 --version`。需要 Python 3；Windows 若只提供 `py`，可把下文的 `python3` 换成 `py -3`。没有 Python 时从 Python 官方渠道安装，不运行未知安装命令。
3. 输入 `cd `（最后有一个空格），把文件夹拖入终端，回车。输入 `ls` 查看文件；Windows 命令提示符可用 `dir`。不要在保存密钥或工作隐私数据的目录练习。
4. 执行 `python3 lab_pack.py --help` 查看参数；运行第一课：`python3 lab_pack.py basics --output basics-01.json`。
5. 终端只显示简短摘要。用文本编辑器打开输出 JSON 看完整数据。JSON是结构化记录：冒号左边是字段名，右边是值；`[...]`是列表，`{...}`是一组字段。
6. 每次改参数请换输出文件名。脚本拒绝覆盖旧结果；这不是故障，是为了保留证据。不要加 `-O`，它会关闭断言检查，脚本会拒绝运行。

**三类证据不能混淆：** `matrix` 和 `compare` 有你本机的真实CPU计时；`queue` 是离散事件模拟；其他命令是确定性数值计算或合成数据统计。全部输入都是人工生成数据，不是生产用户请求。`source` 字段逐份说明来源。平台提交JSON只能检查内部一致性，不能证明你独立运行或真实机器身份。


## 2. gradient：有限差分核对梯度

```sh
python3 lab_pack.py gradient --epsilon 0.00001 --output gradient-01.json
```

模型仅一个权重：预测=`w*x`，损失=`(预测−目标)²`。链式法则给出 `dL/dw=2*(w*x−target)*x`。有限差分通过轻微改变权重，比较两侧损失：`[L(w+h)−L(w−h)]/(2h)`。

这里 `x=1.5,target=3,w=1.2`，解析梯度为−3.6。负号表示稍增权重会降低损失。更新 `w_new=w−0.05*梯度` 后损失应下降。输出包含不同epsilon下的误差；epsilon不是越小越好，浮点数相减可能丢失有效位。

修改任务：把目标改成1，先预测梯度正负，再修改对应断言；尝试把学习率改成很大，观察损失是否反而增加。**不要因此删掉“下降”的断言**：保留失败记录，解释它揭示学习率条件不满足。

验收：解析与数值梯度误差<1e-5；展示一例下降和一例过大学习率失败，并解释。局限：这是光滑二次函数，不证明整张神经网络的梯度正确，ReLU拐点也不能直接套用相同检查。

## 3. matrix：先正确，再计时

```sh
python3 lab_pack.py matrix --size 20 --repeats 7 --output matrix-n20.json
python3 lab_pack.py matrix --size 40 --repeats 7 --output matrix-n40.json
```

矩阵乘法把左矩阵的一行与右矩阵的一列逐元素相乘后相加。`test_matrix`包含2×2、行乘列、非方阵以及不合法形状。脚本预热一次，不计入时间，再用单调高精度计时器记录每次运行。

看 `timing.samples_ms`（全部原始时间）、`median_ms`、`p95_ms`、`count`。最近秩p95取排序后第 `ceil(0.95*n)` 项；7次测量时它就是最大值，所以不能当成稳定生产长尾。

修改任务：先预测边长翻倍时三重循环的运算量约变8倍，再计算实测中位数比值。自增一个3×2乘2×4测试；另加非法“参差不齐”矩阵测试。矩阵规模限2..64，重复次数5..30，避免误操作长时间占CPU。

验收：所有正确性断言通过；提交原始时间而非只报最快一次；解释系统负载、Python解释开销、内存访问为什么让时间比不精确等于8。这里不是BLAS，也不是GPU推理。

## 4. trace：端到端分位数不是各段分位数相加

```sh
python3 lab_pack.py trace --output trace-01.json
```

程序生成20条教学请求：排队、计算、后处理，各请求总时间等于三段之和。先对总时间排序，再求p50/p95。先分别求每段p95再相加，通常不能得到总时间p95，因为慢的请求不一定是同一条。

看 `traces`、`p95_ms`、`sum_of_component_p95_ms`、`maximum_ms`。注意一个极慢请求在20条里可能位于最大值，未必出现在p95里；“p95没变”不能证明所有用户都没变慢。

修改任务：把最慢请求改成更慢，预测p95与最大值分别变化多少；再让两条请求变慢。保留修改前后数据，手工确认第19项与第20项。

验收：写出排序后的总耗时，指出使用的分位数定义和样本数；解释为何不能由这些合成记录得出真实服务结论。

## 5. quantization：量化范围与位宽的取舍

```sh
python3 lab_pack.py quantization --bits 4 --clip 2 --output quant-4b-2.json
python3 lab_pack.py quantization --bits 8 --clip 2 --output quant-8b-2.json
python3 lab_pack.py quantization --bits 4 --clip 3 --output quant-4b-3.json
```

对称量化使用 `qmax=2^(bits−1)−1`，`scale=clip/qmax`。先除以scale，再四舍六入五成双（Python round的ties-to-even规则）得到整数，最后裁剪到整数范围。还原为 `整数*scale`。

位数增加会让同一范围内档位更细；扩大范围避免裁剪离群点，却让档位变粗。输出每个值的整数、还原值、误差和是否裁剪。未裁剪值误差≤半个档位；被裁剪值不受这个界约束。

修改任务：给输入加入一个大离群值10，比较clip=2和clip=10；解释为什么不能只说“8位一定让模型任务分数更好”。自增测试：零值还原准确、极端值发生裁剪、未裁剪误差满足界。

验收：手算一个值的量化过程；记录MSE及最大错误样例。这里只是标量模拟，不包含模型校准、per-channel scale或真实低精度内核。

## 6. memory：从公式建立显存预算

```sh
python3 lab_pack.py memory --tokens 4096 --batch 4 --output memory-small.json
python3 lab_pack.py memory --tokens 32768 --batch 8 --output memory-large.json
```

KV字节数=`2*层数*KV头数*头维*token数*并发*元素字节`。前面的2代表K与V，KV头数不一定等于Query头数。程序固定32层、8个KV头、128维、每元素2字节。默认结果为2GiB。

教学卡容量24GiB，权重8、工作区4、余量2，因此KV预算10GiB。所有GiB按2³⁰字节，不是十进制GB。`payload_fits_budget`只说明这个简化payload估算满足预算，不代表模型一定能上卡。

修改任务：先手算长度翻倍/并发减半的影响；修改工作区为6GiB，重新计算预算。列出公式遗漏的碎片、页分配和动态临时张量。

验收：单位一致，写出每个因子含义；分别展示估算满足和不满足的例子。**本命令没有访问GPU，也没有测真实显存。**

## 7. queue：吞吐容量与用户等待

```sh
python3 lab_pack.py queue --rate 50 --batch 4 --output queue-light.json
python3 lab_pack.py queue --rate 300 --batch 4 --output queue-overload.json
python3 lab_pack.py queue --rate 50 --batch 8 --output queue-b8.json
```

模拟120个匀速到达的请求，一个FIFO服务台，满一批才处理；批服务时间=`8+2*批大小`ms。服务开始时间取“该批最后一个请求到达”和“上一批完成”中较晚者。最后一个不完整批在有限trace结束时排空，因此不是严格无限流满批系统。

容量=`1000*批大小/(8+2*批大小)`请求/秒。默认批4容量250req/s。到达300req/s长期超过容量，积压随时间增加。有限120条依然能算p95，但它不是稳定系统长尾。更大batch既分摊固定成本，也增加凑批等待，不是无条件更好。

修改任务：固定rate扫描batch=1/4/8/16，列出容量、p95、最后请求等待；手工验证前两批的开始/结束时间。再固定batch比较低负载与过载。

验收：解释“模拟时钟”不是真实CPU用时；指出匀速、无超时、无随机性、有限请求数这些假设。提出真实生产还需要哪些突发流量与超时测试。

## 8. compare：公平地比较一次优化

```sh
python3 lab_pack.py compare --size 20 --repeats 15 --output compare-n20.json
python3 lab_pack.py compare --size 40 --repeats 15 --output compare-n40.json
```

基线每次读取右矩阵的一列；候选先把右矩阵转置成可顺序读的列。候选代码是完整实现，不是留空练习。计时包含每次转置成本；两者均先运行一次预热。每轮交替先运行谁，避免总让同一个方案受首次计时偏差。正确性先对照，最大绝对误差须≤1e-10。

读 `baseline` 与 `candidate` 的全量时间。加速比=`基线中位数/候选中位数`；耗时下降比例=`1−候选/基线`。10ms→6ms是约1.67倍加速、40%耗时下降，不是67%耗时下降。候选可能更慢，程序仍正常保存真实结果，不挑选好看的运行。

修改任务：在副本添加“转置后复用”实现，分别报告“含预处理端到端”和“预处理已完成”两个口径，不能混比；保持相同输入/随机种子。至少补两种规模和非方阵正确性测试。

验收报告模板：

- 假设：改变什么访问模式，预期为什么有效？
- 控制：输入形状、随机种子、Python版本、系统负载、预热、重复次数。
- 正确性：测试列表与最大差异；失败案例也保留。
- 性能：全部原始时间、中位数、p95、加速比；说明小样本局限。
- 反证：哪些规模更慢？是否把转置成本漏算？
- 结论：仅针对本机这次CPU实验，不推断所有硬件或真实模型。

## 常见错误与安全边界

- `can't open file`：当前目录不对，用`ls`/`dir`确认脚本位置。
- `Output exists`：换一个新输出名，不删除之前证据来“重试”。
- 参数范围错误：按`--help`和错误提示缩小范围。无需提高限制就能完成本包。
- `AssertionError`：先理解哪条正确性条件不成立；不要删断言来制造通过。
- 找不到输出目录：`--output`的父目录须已存在；初学先写当前目录简单文件名。
- 结果更慢：是允许的真实结果；保留它并检查系统负载、规模、口径，不反复跑到出现漂亮数字才交。
- `-O`被拒绝：这是为了防止Python跳过断言却仍打印测试通过数。
- 不把日志中的密钥、私有生产输入、客户信息放入报告。本包只需合成数据。
