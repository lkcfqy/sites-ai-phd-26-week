# 真实 LLM 服务专项：有界本地 vLLM 实验

## 它解决什么缺口

小型分类器的HTTP服务能教会接口、校验和测量，但没有真实token生成、prefill/decode、KV cache和LLM调度。本项目把这些能力单独设为验收门槛，不能用浏览器队列模拟或Python小模型抵扣。

**当前验证状态（2026-10-23）：**`prepare.py`与`inspect_result.py`的3组标准库测试已在CPU运行；这里没有vLLM/NVIDIA运行环境，没有加载模型、启动GPU服务、生成token或取得GPU性能数据。命令按当日官方CLI核查，仍必须与学习者实际安装版本的`--help`核对。本包不是已经通过的真实服务实验。

## 先修与资源

完成C++/CPU基准、真实CPU模型、HTTP负载、attention/KV/TTFT课。需要已经获准使用的兼容NVIDIA设备、经许可且已在本地的完整模型与tokenizer、合适vLLM安装。**A100必须另行询问用户；不能因为课程有下一步就自动使用。**不要求购买显卡或新API密钥；硬件未具备时可做计划和日志分析，真实能力保持待验证。

模型必须选择能够在授权设备预算内运行且被实际vLLM版本支持的本地模型。确认模型来源、许可证、文件完整性和是否需要远程自定义代码；本包不启用`trust_remote_code`，不下载任何模型，不读取私有对话。不要为使大模型跑起来自动增加显存比例、上下文、并发、收费时间或安全权限。

## 第1步：理解要测的东西

- **Prefill**处理prompt；**decode**逐步生成。长prompt与长输出不是同一种负载。
- **TTFT**要注明客户端到首token或服务器到首token的边界。客户端还包含网络与调度。
- **ITL**是相邻token时间间隔；平均TPOT不能替代ITL分布。
- **吞吐**可指请求/s或输出token/s；固定请求数不表示输出token完全相同，EOS可能提前结束。
- **KV**受层数、KV heads、头维、上下文、并发和字节影响；量化权重不自动代表KV也量化。
- **SLO**是本次任务约束，不是普遍行业标准。先写自己的允许尾延迟、失败率和质量门槛，再看结果。

## 第2步：只生成计划，不运行GPU

在新目录解压，核对Python与本地模型路径：

```sh
python3 test_tools.py
python3 prepare.py --model-dir /你的已授权本地模型目录 --output-dir run-plan-01 --requests 32 --rate 1 --concurrency 1
```

`prepare.py`仅检查目录/config存在，生成`plan.json`与`commands.txt`；不会导入vLLM、联网、申请资源或执行命令。模型目录存在也不能证明兼容或许可。计划限制16–128请求、0.1–5请求/s、并发1–4，固定短输入/输出起步。默认32条只用于流程验证，远不足稳定估计生产P99。

## 第3步：核查环境并得到明确授权

记录GPU型号、驱动、CUDA、vLLM、Python、模型/tokenizer版本或文件hash、预算与截止条件。使用独立环境，按官方安装文档选择兼容方案，不安装来源不明wheel。先看：

```sh
vllm --version
vllm serve --help
vllm bench serve --help
```

检查实际CLI是否支持生成计划的参数。若不同，保存版本和错误，根据对应官方文档修改计划并保留diff。不要删除必要计量字段后仍宣称完整验收。

## 第4步：人工运行本地服务与有界负载

阅读`commands.txt`后，在**已获授权**环境的专用终端A手动运行其中的服务命令，终端B运行benchmark命令。服务仅绑定127.0.0.1，不公开外网。环境变量阻止模型hub下载并关闭可选usage统计；不使用私有数据。初始配置限制上下文1024、最多4活动序列、显存比例0.5；这些不是保证适合所有模型的值，放不下就报告限制或选已授权的小模型，不能自动扩大预算。

等待服务明确就绪，先发少量请求验证。按计划记录4次warmup、32次测量、输入128token、输出上限64token，保留详细每请求结果。请求率是目标到达率，最大并发可能使实际到达受限制，因此同时记录实际吞吐与客户端排队；不要把这次有界测试当无限开放负载。

**停止条件：**许可/预算到期、持续错误、OOM、温度或系统监控超限时停止新请求，在终端A用Ctrl-C只关闭自己启动的服务并确认资源释放。不通过无界重试延长预算，不杀未知进程。

## 第5步：检查原始数据，而不是只看摘要

```sh
python3 inspect_result.py run-plan-01/benchmark.json --expected-requests 32 --output artifact-check-01.json
```

该工具仅检查已知schema字段与内部一致性，不证明机器身份、日志真实性或模型质量。若实际版本输出结构变化，明确失败并修改解析器和测试，不能填造缺失字段。查看：完成/失败数、原始TTFT/TPOT/ITL（若工具提供）、实际输入输出长度、测量时长与吞吐；没有详细ITL数据时，不从平均值伪造分布。

随机token负载用于长度/调度测量，不评价语言质量。另建立有权限的、可追溯的小任务质量集，冻结模型、采样设置和评价协议；不能由benchmark正确返回HTTP 200推断答案质量合格。

## 第6步：独立实验，而非复制命令

1. 固定模型、版本与硬件，改变一个因素：并发1→2→4，或输入长度/输出上限；每次重新生成新目录计划，保留所有结果。
2. 提出两种瓶颈解释，例如prefill成本和排队，写出哪种观测能证伪；不要只凭GPU利用率下结论。
3. 加入长短请求混合负载，记录实际长度分布；这一扩展由学习者实现，不能只改总体平均长度冒充混合负载。
4. 观察一次失败或无收益配置。写出失败影响、缓解、根因候选、验证与回滚，不为了“成功”删除日志。
5. 采集可获授权的指标/trace；没有计数器权限时注明，不修改安全策略绕过。

## 陌生任务验收

提交源码/配置diff后，评审再给一个新长度分布、SLO或内存预算。学习者需要独立：检查资源→建立基线→定义指标→计划对照→执行授权实验→检查质量与尾延迟→决定接受/拒绝→交接与回滚。至少一个任务应在未提前给定答案的情况下完成。

交付：环境清单、授权资源边界（不含密钥）、模型许可来源、计划与变更、全部原始结果、质量集协议、错误/失败记录、统计脚本、报告、回滚和停止清理记录。自动上传或结构检查只证明“提交材料”，不授予岗位认证。
